# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

- **The author, triaging a regression.** Opens `out/<run>/dashboard/index.html` after a
  `make quick` / `make full` run to see what failed, which bucket, which seed to replay,
  and which coverage bins are still holes.
- **Interviewers and recruiters (primary audience for the dashboard's presentation).**
  Meet it through the README screenshot or the shared HTML file, usually for under a
  minute, with no context about the run. The project targets an ASIC Design &
  Verification internship (Cisco Silicon One JD).

## Product Purpose

packet-router-verif verifies a small 4×4 store-and-forward packet router (SystemVerilog)
with a UVM-style C++17 testbench on Verilator, run by a Python pipeline that compiles
once, runs hundreds of seeds in parallel, merges functional and code coverage, buckets
failures and writes an offline dashboard. The design is small on purpose; the testbench
and automation are the product. Success for the dashboard: in about 30 seconds an
interviewer believes **verification is closed**: every requirement checked, coverage
closed with honest, visible waivers, and the run reproducible.

## Positioning

A regression report that shows its own provenance: every number names the file it came
from (R-PY-04), waivers are counted rather than hidden, and the closure curve admits
where random stimulus stopped finding new bins.

## Operating Context

- Generated by `scripts/dashboard.py` from `scripts/templates/dashboard.html.j2` into
  each run folder; opened from disk (`file://`) or a local static server.
- Inputs: `results.json`, `func_cov_merged.json`, `code_cov.json`, `closure.json`,
  `jobs/*/summary.json`.
- Runs on WSL2 Ubuntu with Verilator 5.032 (no expression coverage).

## Capabilities and Constraints

- One self-contained HTML file; no network at runtime: no web fonts, CDNs or external
  scripts (R-PY-02). Charts are inline SVG drawn by `scripts/dashboard.py`; fonts are embedded as data URIs.
- Python 3.10+, standard library plus jinja2 (pyyaml for suites; fontTools only to rebuild the embedded fonts).
- Panels required by the spec (section 10.3): KPI row (runs, pass rate, functional %,
  line %, toggle %, expression %, wall time, git commit); results by test with failing
  seeds and repro commands; failure buckets; functional coverage per covergroup with bin
  tables, holes highlighted, crosses as heat grids; code coverage per module and type
  with links to the genhtml report and annotated source; closure curve; performance
  (latency histogram, throughput per output).
- Must render the failing state as well as the passing one (failed runs, buckets,
  holes, uncovered points, expression coverage "n/a").

## Evidence on Hand

Real data from real runs: `out/full/` (527 runs, 100% pass, 100% functional, line 100%
with 4 waived points, toggle 100%), mutation runs in `out/bug_*/` with real failures and
buckets. No testimonials, users or benchmarks exist; none may be invented.

## Product Principles

1. Every number is traceable to a file in the run folder.
2. Honesty over polish: waivers, n/a metrics and coverage-closure speed are shown, not hidden.
3. Triage first: a failure, its bucket and its repro command are never more than a glance away.
4. Density is a feature: bin-level detail stays visible, not buried behind clicks.
